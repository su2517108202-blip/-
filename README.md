# 设计框架库

保存每个项目已落地的前端设计和可复用代码。下次改版或加功能时，先按项目和设计找到原实现，再沿已有入口扩展。

## 一个项目一个目录，独立设计分别保存

目录统一为 `<项目名>/<设计名>/`。顶层用产品或项目的稳定名称，子目录用能辨认用途或方向的名称，例如「品牌官网」「编辑工作台」。归档前先查已有目录及其说明，确认属于同一产品、同一设计。

| 遇到什么变化 | 保存到哪里 |
| --- | --- |
| 开始另一个产品，即使风格或技术栈相近 | 新建该产品的顶层目录，再建它自己的设计目录。 |
| 同一产品增加独立的官网、工作台，或需要并行保留另一套完整设计 | 在该产品下新建设计子目录。若有并行方案，在各自说明里写清用途和采用状态。 |
| 同一设计增加页面、功能、响应式适配或修正交互 | 更新原设计目录。历史版本通过 Git 提交查找。 |
| 同一产品的多套设计实际共用一份代码或素材 | 在项目内保存一份，各设计从说明和代码指向同一来源。其他产品保留自己的设计目录。 |

## 每份设计留下什么

每个设计目录放一份简短的 `README.md`，连同能独立运行或接入原宿主的框架源码、必要素材及依赖信息一起保存。沿用项目已有的文件结构。说明应包含以下内容。

1. 这份设计服务哪个产品和任务，怎样启动或在宿主中打开，走哪条路径能看到结果。
2. 采用了哪些参考、具体借用了什么，以及真实内容怎样影响布局、素材或动效的选择。
3. 用一项已完成的功能指出入口、共用布局或组件、样式和数据来源的真实文件或符号，让下一位开发者知道从哪里接入。
4. 修改共享部分后，怎样从已有入口和本次变更入口复验。依赖特定宿主或数据时写清条件。

## 如何更新

先同步远端，阅读对应设计的说明和实现。原框架能够承接的新功能直接接入。多个页面出现同一问题时，改动共用来源并复验受影响的使用处。若变更影响接入方式，同步更新该设计的说明。

本库公开。归档前检查本次差异，只提交相应项目的框架及可公开分发的依赖或素材。私有配置、密钥、客户数据和未经许可的素材留在原项目，需要说明效果时使用可公开的代表数据。

在正确的目录验证运行或宿主接入，推送后核对远端目录和提交。交付指向具体设计的链接。首个正式项目开始归档时再创建项目目录。
